# AI 오케스트레이션 운영 규칙

> **어디에 쓰는 문서야?** Orca·Freebuff·OpenCode(Sol)로 AI에게 일을 나눠 맡기는 환경에서만 복사해 줘. 이 도구가 없는 프로젝트에는 복사하지 않거나 `해당 없음`으로 남겨줘.
> **무엇을 기준으로 썼어?** 2026-11-18 `D:\project\eGovFrameDev_RECS\workspace`에서 직접 확인한 내용을 Arkive에 맞게 옮겼어. 모델·요금·시간 규칙이 바뀌면 다시 확인해서 고쳐줘.
> **이 PC에서도 확인했어?** 2026-11-18 Arkive 작업 PC(`C:` 드라이브만 있음)에서 Freebuff·OpenCode2에 읽기 전용 작업을 맡겨 다시 확인했어(9장). 원 기록의 `D:\` 경로는 이 PC에 없으니 관련 항목은 `미확인`으로 남겨뒀어.

이 문서는 **현재 대화를 맡은 AI가 다른 AI에게 일을 나눠 맡길 때** 읽는 안내야. 여기서는 현재 대화를 맡은 AI를 **총괄**, 따로 일을 맡는 AI를 **Worker(작업 담당 AI)**라고 부를게.
모드 전환·자동 제안·추론 강도 제안의 기본 규칙은 [AGENTS.md](../../../AGENTS.md#ai-오케스트레이션)에 있어. 이 문서에서는 실제로 일을 맡기고 결과를 확인하는 방법을 설명할게.

## 빠른 실행 체크리스트 (총괄용)

다른 AI에게 일을 맡기기 전에 아래 순서대로 확인해 줘.

1. **사용자가 허락했는지 확인해 줘.** 오케스트레이션 모드가 아니면 1장 형식으로 먼저 물어봐. 거절하거나 답이 없으면 혼자 처리해 줘.
2. **이미 작업 중인 내용부터 확인해 줘.** `git status`로 기존 변경을 보고, `orca status --json`과 `orca terminal list --json`으로 열린 작업 상태를 확인해 줘.
3. **시간 차감과 실행 준비를 확인해 줘.**
   - Freebuff는 `Get-Process freebuff`와 `~/.config/manicode/freebuff-live-*.json`으로 이어받을 세션을 확인하고, 실행 전 Flash 설정과 화면 상태를 대조해 줘(4.2·4.3절). 파일 전체를 출력하지 말고 인증 값을 뺀 필요한 항목만 확인해 줘. 새 세션이 필요하면 **일일 할당에서 2시간이 차감된다**고 먼저 알려줘.
   - Sol을 써야 할 때만 `netstat -ano | findstr "127.0.0.1:8790"`으로 KR bridge가 켜져 있는지 확인해 줘(3장).
4. **읽기 쉬운 작업 지시서를 써줘.** 7장의 구어체 템플릿을 채워 `.md` 파일로 전달해 줘. 금지 표현은 쓰지 말고, 목표·읽을 파일·수정 범위·금지 사항·근거·완료 증거를 빠뜨리지 마. GUI 작업은 승인된 테스트 환경과 데이터 범위도 적어줘(6.1절).
5. **결과는 직접 확인해 줘.** 작업을 시작한 뒤에는 차례를 마치고 Orca가 결과를 알려줄 때까지 기다려줘. 결과를 받으면 `verify.cmd`와 ego-browser 화면을 총괄이 직접 확인하고 판단해 줘. 이번 변경이 Markdown 문서뿐이면 [AGENTS.md](../../../AGENTS.md)의 예외에 따라 `verify.cmd` 대신 링크·앵커를 확인해 줘.

## 1. 모드 전환

- **처음에는 혼자 처리해 줘.** 사용자 허락 없이 Worker를 만들거나 Orca orchestration 명령을 실행하지 마. 새 세션은 항상 `일반 단독 처리 + 자동 제안`으로 시작해 줘.
- **나눠서 하면 도움이 될 때만 한 번 물어봐 줘.** 작업이 크거나 서로 독립된 부분으로 나눌 수 있으면 시작 전에 제안해 줘.
  - 이렇게 물어봐 줘: "Worker에게 나눌까요? (배정안: Freebuff ○○ / Sol ○○, 예상 소모: Freebuff 세션 ○ / Sol 사용 여부)"
  - 예를 들면 소스 조사와 기능 이식을 나누는 작업, 여러 화면·계층에 걸친 구현, 구현과 별도 검증을 나누는 작업, 여러 프로젝트를 비교하는 조사야.
  - 승인하면 나눠서 진행하고, 거절하거나 답이 없으면 혼자 처리해 줘. 간단한 질문·조회·설명이나 한두 파일의 작은 수정에는 제안하지 마.
- **켜달라고 하면 이 대화에서 계속 적용해 줘.** `오케스트레이션으로 진행해줘`, `오케스트라로 해줘`, `Worker에게 나눠서 진행해줘`라고 하면 이후 작업도 오케스트레이션으로 진행해 줘.
- **그만 쓰라고 하면 바로 멈춰줘.** `일반 모드로 전환해줘`, `오케스트레이션 중지`, `Worker를 사용하지 마`라고 하면 즉시 혼자 처리하고, 그 세션에서는 자동 제안도 하지 마.

## 2. 추론 강도 제안

- 추론 강도는 AI가 문제를 얼마나 깊게 검토할지 정하는 설정이야. 총괄이 자기 설정을 직접 바꿀 수는 없으니 사용자가 바꿔줘야 해.
- 어렵거나 중요한 작업이면 시작 전에 한 번만 제안해 줘: "이 작업은 강도를 올리는 게 좋겠습니다 (이유: ○○). 높여서 진행할까요?" 요청에 `ultrathink`를 붙이거나 세션 effort 설정을 올리는 방법도 함께 알려줘.
  - 원인 불명 오류, 권한·인증·데이터 정합성 수정, 여러 계층 변경, 기능 이식 설계, DB 스키마·마이그레이션 변경처럼 판단이 중요한 경우가 해당돼.
- 단순 조회·설명·한두 줄 수정에는 제안하지 말고, 같은 작업에서 반복해서 묻지 마.
- 사용자가 거절하면 현재 강도로 진행하되 검증을 더 꼼꼼히 해줘. 불확실한 내용은 보고에 남겨줘.
- Worker의 모델·강도도 총괄이 임의로 바꾸지 마. 설정 방법은 3장을 확인해 줘.

## 3. 역할 구성과 모델 (2026-11-18 실측 기준)

| 역할 | 에이전트 (Orca agent id) | 실제 모델 | 사용 기준 |
| --- | --- | --- | --- |
| 총괄 | 현재 대화를 맡은 AI (기본: Claude Code) | - | 요청 분석, 작업 분배, 결과 비교·검증, `verify.cmd`·GUI 최종 확인, 최종 판단과 보고 |
| 주로 일을 맡길 AI | Freebuff (`freebuff`) | DeepSeek V4.1 Flash · high (2x, 기본값. 2026-11-18 이 PC의 Freebuff 화면 하단 표시로 확인) | 대부분의 분석·구현·검증. 무료, 아래 시간 규칙 적용 |
| 대체할 AI | OpenCode2 (`opencode2`) | GPT-6.1 Sol (AgentRouter, `ar-sol/gpt-6.1-sol`) | Freebuff가 불가할 때, 또는 어렵고 중요한 판단·최종 리뷰. 실제 배정은 아래 우선순위를 따라줘 |

- **Freebuff부터 써줘.** 시작 실패·제한 도달·반복 오류로 Freebuff를 쓸 수 없을 때만 OpenCode2(Sol)로 바꿔줘.
- **Sol은 비용이 드니 하루 약 $20 이내로 써줘.** AgentRouter 잔액에서 차감돼. 작업 범위와 읽을 파일을 좁혀 토큰을 아끼고, 오늘 한도에 가까운지 모르겠으면 맡기기 전에 사용자에게 확인해 줘.
- 실제로 실행된 모델이 위 표와 다르면 그냥 진행하지 말고 먼저 알려줘.
- **모델·강도는 이렇게 확인해 줘.**
  - Freebuff는 Orca `--model`/`--effort`로 지정할 수 없어(`worker-start --help` 확인). 바꿔야 하면 사용자에게 요청해 줘. Freebuff 화면에서는 `/model` → `↑↓`로 모델 선택 → `Tab`으로 추론 강도 변경 → `Enter`로 확정해(2026-11-18 사용자 화면 확인).
  - OpenCode2(Sol)도 Orca `--effort`를 지원하지 않아.
- **Sol을 쓰기 전에 KR bridge를 확인해 줘.** 이 PC의 OpenCode2는 로컬 중계 프로그램을 거쳐 접속해. 설정은 `~/.config/opencode/opencode.jsonc`, 주소는 `http://127.0.0.1:8790/v1`, 중계 코드는 `~/.config/opencode/kr-bridge/proxy.js`야. 한글 때문에 `400 content-blocked`가 나면 이스케이프로 1회 재시도해.
  - 중계 프로그램이 꺼졌거나 멈추면 오류 없이 기다리기만 하니, 배정 전에 `netstat -ano | findstr "127.0.0.1:8790"`으로 `LISTENING`을 확인해 줘.
  - 켤 때는 바탕화면 `AgentRouter KR bridge` 또는 `kr-bridge/start-bg.cmd`를 써줘(창 없이 실행, 로그 `kr-bridge/bridge.log`, 이미 켜져 있으면 알림만 표시). 끌 때는 `kr-bridge/stop.cmd`를 써줘. 재부팅 후에는 다시 켜야 해.
  - 콘솔 방식(`kr-bridge/start.cmd`)은 창 안을 클릭해 제목에 "선택"이 붙으면 중계가 멈춘 사례가 있어(2026-11-18 관측). 그때는 `Esc`를 누르거나 다시 시작해 줘.

## 4. Freebuff 사용 규칙

### 4.1 시간과 차감

- 하루 할당은 15시간(기본 12 + 연속 사용 보너스 3)이고, `00:00(Asia/Seoul)`에 초기화돼. `1시간 = 5 freebucks`야.
- 기본은 **DeepSeek V4.1 Flash · high (2x)**로 써줘. 새 세션을 열면 **일일 할당에서 2시간이 차감되지만, 실제로 쓸 수 있는 시간은 1시간**이야(2026-11-22 사용자 재확인). 사용자가 따로 모델 변경을 지시하지 않으면 다른 모델·차감 기준으로 시작하지 마.
- 만료 시각은 시작할 때 정해져. 터미널을 닫아도 시간은 계속 흐르니, 작업을 살아 있는 1시간 안에 묶어서 맡겨줘. 짧은 작업 하나 때문에 새 세션을 열지 마.
- 남은 일일 할당이 다음 세션 차감량(2시간)보다 적거나, 세션이 없는데 작업이 짧으면 총괄이 직접 처리하거나 사용자에게 물어봐 줘.
- 허락 없이 `End session`을 누르거나 세션을 종료하지 마. 다시 시작하면 남은 시간을 잃고 다시 차감돼.

### 4.2 세션 소유와 이어받기

- **세션 하나는 실행 중인 Freebuff 프로그램 하나가 맡고 있어**(2026-11-18 이 PC 실측, Freebuff 0.2.36).
  - `~/.config/manicode/freebuff-live-<PID>.json`의 `instanceId`·`ownerPid`·`expiresAt`·`model`로 확인할 수 있어. 같은 파일의 `tokenKey` 등 인증 값은 절대 출력·기록하지 마.
  - 맡고 있던 프로그램이 꺼졌고 만료 전이면 새 프로그램이 **같은 세션을 이어받아**. `instanceId`·`expiresAt`이 같고 일일 시간도 다시 차감되지 않았어(23:02·23:30에 연 프로그램이 22:44 시작 세션을 이어받고, `35m left`·`2/15 hours`가 유지된 실측).
  - 기존 프로그램이 살아 있으면 같은 세션을 공유하지 못해. 새 Worker가 별도 세션을 열고 추가 차감된 사례가 있어(23:04 실측).
  - 첫 화면의 `○m left`는 남은 시간이 있는 세션을 이어받았다는 뜻이야. "Your first message starts the session"은 첫 메시지를 보내면 새 세션이 시작된다는 뜻이야.
- **새로 띄우기 전에 이렇게 확인해 줘.**
  1. 라이브 파일과 `Get-Process freebuff`로 만료 시각과 기존 프로그램이 살아 있는지 확인해 줘. 기존 프로그램이 없고 만료 전인 세션이 있으면 이어받을 수 있어. 파일은 첫 메시지 제출 무렵 생기니 막 띄운 직후에는 없을 수도 있어(2026-11-21 관측). 이때는 첫 화면 표시로 확인하고, **화면에 살아 있는 세션이 있으면 새 Worker/Freebuff를 띄우지 마**.
  2. 이어받을 세션이 있으면 `worker-start --agent freebuff`로 띄워줘. 첫 화면 모델이 Flash인지, `○m left`와 `○/15 hours remaining`이 유지되는지 대조해 줘. 다른 모델이나 새 세션 시작 창이 뜨면 진행하지 말고 4.3절을 따라줘.
  3. Worker가 끝나 자동으로 닫힌 뒤에는 만료 전 세션을 다음 Worker가 이어받을 수 있어. Freebuff는 `--keep-open`을 쓰지 마(5장).
  4. 이어받을 세션이 없을 때만 새로 시작하고, **일일 2시간 차감**을 사용자에게 먼저 알려줘.
- **실행 중인 Freebuff에 추가 지시를 넣지 마.** `orchestration send`나 `worker-start --terminal`로 보낸 지시가 입력창에 첨부(📄)로만 붙고 제출되지 않았고, Enter·지우기 키에도 반응하지 않았어(2026-11-18 23:17~23:27 실측, 원인 미확인).

### 4.3 Flash 기본값과 실행 확인

- **기본은 Flash · high (2x), 새 세션당 일일 2시간 차감으로 고정해 줘.** Flash Fast나 다른 모델의 시작·추가 차감을 허용하는 안내는 쓰지 마.
- `~/.config/manicode/settings.json`의 `freebuffModelKey`에는 Flash가 저장돼 있지만, Freebuff 0.2.36에는 시작 모델을 지정하는 `--model` 옵션이 없어. 모델 목록을 불러오기 전 첫 제출이 Flash Fast로 시도된 사례가 있었어(2026-11-18). 예외 동작을 기록한 것이지 다른 모델 사용을 승인한 게 아니야.
- **시작 전 Flash 설정과 이어받을 세션을 확인해 줘.** 실행 직후에도 실제 모델·남은 시간·차감량을 대조해 줘. 다른 모델이나 "새 세션 시작" 창이 뜨면 승인하지 말고 사용자에게 Flash 선택을 요청해 줘(`/model` → Flash 선택 → `high` 확인 → `Enter`). Worker 작업 지시를 터미널 키 입력으로 조종하지 마.
- 이어받을 세션이 없고 첫 제출 모델을 보장할 수 없으면 새 Worker를 바로 시작하지 마. 사용자에게 Flash 세션을 먼저 준비해 달라고 하고, 일일 2시간 차감 조건을 확인한 뒤 진행해 줘.

### 4.4 동시 실행 시 계정 분리

- **화면 검증을 동시에 할 때 같은 계정을 쓰지 마.** Arkive는 중복 로그인 방지가 있어서 한 Worker가 `admin`으로 로그인하면 다른 Worker의 같은 계정 세션이 끊겨(2026-11-18 A1·H 동시 실행 실측). `127.0.0.1`과 `localhost`를 나눠도 해결되지 않았어. 관리자 작업은 순서대로 하거나 Worker마다 테스트 계정을 따로 지정해 줘.

### 4.5 잔여 시간·만료 확인

- **현재 세션의 남은 시간은 확인할 수 있어.** 라이브 파일의 `expiresAt`으로 만료 시각과 남은 분을 계산해 줘. 인증 정보는 출력하지 마(2026-11-21 실측: `21:42:51 − 20:44:51 = 약 57분`, `freebuff.exe` PID `14484` / `ownerPid 14484` 정상 확인).
- **일일 15시간 중 남은 양은 아직 `미확인`이야.** 원 기록 PC의 조회 명령은 `node D:/project/eGovFrameDev_RECS/workspace/.freebuff-usage/usage.mjs --once --full`이지만, 이 PC에는 `D:` 경로가 없어. 새 세션을 열기 전에는 일일 2시간 차감 가능성을 먼저 알려줘.
  - 아직 없는 것: 일일 잔량을 미리 조회할 수단.
  - 필요한 근거/확인자: 조회 스크립트·설정 위치 / 사용자 환경 확인.
  - 보완 방법: `usage.mjs`를 이 PC로 옮기거나 다른 조회 방법을 확인해서 기록해 줘.
  - 완료 기준: 새 세션을 열기 전에 일일 잔량과 차감 가능 여부를 알 수 있어야 해.
- **프로그램과 파일을 확인하는 방법은 정상 동작했어.** 2026-11-21 20:35에 둘 다 없었던 건 세션 등록 전이었기 때문이야(프로그램 20:38:23 시작, 세션 20:42:51 등록). 이후 위 PID·ownerPid·만료 시각을 확인했어. 웹/클라우드 세션 같은 근거 없는 원인은 추측하지 마(9장).

## 5. Worker 종료·재개 동작 (실측)

- 작업이 끝나면 종료 가능한 상태(`reclaimable`)가 되고, 약 10분 뒤(`autoReleaseAt`) 자동으로 닫혀. 닫힌 Freebuff는 이전 대화 기억이 사라져.
- 닫힌 Worker에 `send`를 보내면 새 Freebuff가 열려(`delivery: started_fresh`). 이전 대화 전체가 아니라 Orca가 전달한 보고 요약만 받으니, 다음 지시도 혼자 읽고 이해할 수 있게 써줘.
- OpenCode2처럼 같은 맥락으로 여러 번 일을 맡길 때는 처음부터 `--keep-open`으로 열고, `send` 또는 `--terminal <handle>`로 이어서 보내줘. **Freebuff는 추가 지시가 제출되지 않으니 `--keep-open`을 쓰지 마**(4.2절).
- 한 번으로 끝나는 조사·검증은 `--keep-open` 없이 열어 자동으로 닫히게 해줘. 계속 열어둔 Worker는 일이 끝나면 사용자에게 알리고, 원할 때 닫아줘.

## 6. 작업 배분 원칙

1. 먼저 요청을 이해하고 서로 독립된 일로 나눠줘. 기능 이식은 [AGENTS.md](../../../AGENTS.md)·[PORTING.md](../../../PORTING.md)의 "기능 하나씩" 원칙을 지키고, 한 기능 안에서 조사·구현·검증을 나눠줘.
2. `orca status --json`과 `orca terminal list --json`으로 실제 작업 상태를 확인해 줘.
3. 기본은 Freebuff에 맡기고, Sol은 3장의 조건에 해당할 때만 써줘.
4. **프로젝트 파일을 수정하는 AI는 한 명만 정해 줘.** 여러 Worker가 같은 파일을 동시에 고치면 안 돼.
   - Arkive는 git 저장소라 `--worktree new-child`로 별도 작업 폴더를 만들 수 있지만, 생성·병합·정리 흐름은 아직 검증 전이야. 그전에는 `--worktree current`로 같은 폴더를 쓰고, 별도 폴더는 처음에 작은 작업으로 확인한 뒤 기록해 줘.
   - 시작 전 `git status`를 확인하고, 기존 사용자 변경을 덮어쓰지 않도록 지시서에 수정해도 되는 파일을 정확히 적어줘.
5. 수정이 끝나면 다른 Worker나 총괄이 확인해 줘. 확인 담당에게는 "프로젝트 파일은 생성·수정·삭제하지 말고 조회·검증만 해줘"라고 적어줘. 승인한 검증 명령의 자동 산출물과 지정한 GUI 증거 저장만 예외로 허용해 줘. GUI 데이터 조작은 6.1절의 승인 범위로 제한해 줘.
6. 보고가 서로 다르면 코드·테스트·로그를 근거로 다시 확인하고 총괄이 판단해 줘.
7. **`verify.cmd` 결과와 ego-browser 화면은 총괄이 직접 최종 확인해 줘.** 다른 AI가 "통과했다"고 말한 것만으로 완료 처리하지 마. GUI 확인 방법은 6.1절을 따라줘. Markdown 문서만 바꾼 경우의 검증 예외는 [AGENTS.md](../../../AGENTS.md)를 따라줘.
8. Worker는 커밋·푸시하지 마. 사용자가 요청하면 총괄이 변경을 검토한 뒤 처리해 줘.
9. 마지막 보고에는 실제로 맡긴 AI, 직접 확인한 결과, 미완료 항목만 적어줘. 확인하지 않은 작업을 완료했다고 말하지 마.

### 6.1 GUI 검증 분담 (ego-browser)

화면 조작은 Worker가 할 수 있지만, **최종 검증완료 판단은 총괄만 해줘**. "직접 확인"은 보고서를 읽는 데서 끝나는 게 아니라, **스크린샷을 열어 보고 실제 결과 상태를 다시 조회해서 맞는지 대조하는 것**이야.

| 단계 | 담당 | 내용 |
| --- | --- | --- |
| 시나리오 수행 | Worker | ego-browser로 승인된 순서(등록 → 흐름 진행 → 결과 확인 → 테스트 데이터 정리)를 수행해 줘. 단계별 URL·계정/권한·입력 데이터·기대 결과·실제 결과를 적고 스크린샷을 지정 경로에 저장해 줘. |
| 대조 확인 | 총괄 | 스크린샷을 직접 열고, ego-browser로 결과 화면 또는 DB 상태를 다시 조회해 보고와 맞는지 확인해 줘. 다르거나 증거가 없으면 불합격으로 두고 다시 확인하거나 `미수행`으로 남겨줘. |
| 판정·기록 | 총괄 | [검증 및 변경 로그](../project/verification-log.md)에 기능별로 기록하고, 확인된 결과에 맞춰 `README.md` 상태를 바꿔줘. |

- **데이터를 바꾸기 전에 허용 범위를 확인해 줘.** 사용자가 승인한 테스트 환경에서 지시서에 적힌 계정·테스트 데이터·정리 방법 안에서만 화면으로 등록·수정·삭제해 줘. SQL 등으로 DB에 직접 쓰거나 스키마를 적용하지 마. 운영 데이터와 기존 사용자 데이터는 건드리지 마. 환경·허용 범위·정리 방법이 없거나 불명확하면 쓰기 동작을 멈추고 물어봐 줘. 이 문서나 템플릿 자체가 데이터 변경 허락을 대신하는 건 아니야.
- **증거 저장은 제한된 예외로 허용해 줘.** `target/`을 임의로 바꾸는 건 금지하지만, 이번 작업에 지정한 `target/gui-evidence/<묶음>/`에 새 스크린샷을 만드는 것은 허용해 줘. 기존 증거를 덮어쓰거나 삭제하지 마. 증거는 커밋하지 않고, 총괄이 대조·판정·로그 기록을 마친 뒤 이번 작업에서 만든 것만 정리해 줘. 불합격·보류 증거는 원인 확인이 끝날 때까지 남겨줘. 비밀값과 운영 데이터는 스크린샷에도 노출하지 마.
- **검증 상태 기록은 Worker가 바꾸지 마.** `README.md`와 `docs/ai/project/verification-log.md` 등은 총괄이 기록하니, 수정 허용 범위에서 빼고 금지 사항에 적어줘.
- **화면이 뜨는 것만으로 통과시키지 마.** 등록·수정·삭제·권한 차단 같은 핵심 동작과 결과를 확인해 줘. 여러 기능을 한 줄로 묶지 말고 기능마다 시나리오·결과·증거를 남겨줘. ego-browser를 쓸 수 없으면 다른 브라우저나 데스크톱 자동화로 대체하지 말고 `미수행`과 이유를 적어줘.
- **화면 검증도 기본은 Freebuff에 맡겨줘.** 총괄이 결과를 대조하니 단순 화면 조작에 유료 Sol을 쓰지 마. Freebuff를 쓸 수 없을 때만 3장의 조건을 따라줘.

## 7. Worker 작업 지시서(`.md` spec) 작성 기준 및 구어체 템플릿

작업 지시서는 **이전 대화를 몰라도 이것만 읽고 일을 할 수 있게** 써줘. `.md` 파일로 만들고 `--spec-file <경로>`로 전달하면 돼. Worker에게도 [AGENTS.md](../../../AGENTS.md)의 작업 원칙·품질 관문이 똑같이 적용되니, 필요한 제한을 지시서에 다시 적어줘.

### 7.1 꼭 금지할 표현과 쓰는 방법

**직접 작성하는 작업 지시서·작업 안내·사용자용 결과 보고에는 아래 표현을 절대 쓰지 마.** 이 목록은 금지 대상을 분명히 적기 위한 것이고, 실제 지시서나 안내에 복사하는 예제가 아니야.

- `You are a dispatched worker`
- `Your coordinator receives mail`
- `task ID`
- `dispatch-id`
- `worker_done`
- `총괄이 지시합니다 / worker1` (`총괄이 지시합니다`, `worker1` 각각도 금지)
- `Task:`
- `Requirements` (`Requirements:`도 금지)

대소문자·콜론·띄어쓰기만 바꿔서 같은 표현을 쓰는 것도 하지 마. 대신 **"이번에 확인할 내용", "먼저 읽어볼 파일", "수정해도 되는 범위", "꼭 지켜줄 약속", "끝나면 알려줄 내용"**처럼 사용자가 읽고 이해할 수 있는 말로 풀어줘.

- **동료에게 부탁하듯 써줘.** `~해줘`, `~부탁해`, `~확인해 줘`처럼 자연스러운 구어체를 써줘. 어려운 용어는 무엇을 뜻하는지 짧게 설명해 줘.
- **도구 처리와 읽는 안내를 분리해 줘.** 실행에 필요한 식별자·상태값은 CLI와 도구 처리에서만 다루고, 직접 작성하는 지시서나 사용자용 보고에는 섞지 마. 도구가 자동으로 붙이는 내부 지침은 임의로 삭제·무시하지 말고, 사람이 읽는 안내에는 그대로 복사하지 마.
- **쉬운 말로 바꿔도 내용은 빼지 마.** 아래 6가지 정보와 GUI 시나리오의 URL·계정/권한·입력값·기대 결과·정리 단계·보고 표는 길어져도 빠뜨리지 마.

| 꼭 적어줄 내용 | 이렇게 풀어서 써줘 |
| --- | --- |
| 목적 | 이번에 해결할 문제와 기대 결과를 한두 문장으로 적어줘 |
| 읽을 파일 | 먼저 확인할 경로를 지정해 토큰을 아껴줘. 외부 소스는 확인된 절대경로를 써줘(원 기록 PC `D:\ai\<프로젝트>`, 이 PC 위치 `미확인`) |
| 수정 허용 범위 | 수정해도 되는 파일·폴더를 적어줘. 조사·검증은 프로젝트 파일 생성·수정·삭제 금지로 정하고, 승인된 검증 명령의 자동 산출물과 지정 GUI 증거 저장만 예외로 적어줘 |
| 금지 사항 | 테스트 파일(`src/test/**`) 생성·수정·삭제·skip, 외부 소스·`data/`·`backup/` 및 기존 `target/` 산출물 직접 변경, 실행 중인 DB 직접 쓰기, 비밀값 출력, 커밋·푸시, 검증 상태 기록 수정을 금지해 줘. 스키마는 허용된 정의 파일만 다루고, GUI 데이터 변경은 6.1절 승인 범위로 제한해 줘 |
| 근거 규칙 | 업무 규칙·권한·상태값·DB 의미는 근거 파일과 줄 번호를 적어줘. 근거가 없으면 추측하지 말고 `미확인`으로 남겨줘 |
| 완료 증거 | 변경 파일, 핵심 변경, 실제 실행한 명령과 결과(`verify.cmd` exit code 등), 사용한 버전 식별자(SHA 등), 미완료·미확인 항목을 적어줘 |

### 7.2 바로 복사해 쓰는 구어체 `.md` 지시서 템플릿

아래에서 `<>` 부분을 확인된 값으로 채워줘. GUI 작업일 때만 4절을 넣어줘. 조사·검증이면 수정 허용 범위는 "수정 없음"으로 정하고, 실행해도 되는 명령과 증거 저장 예외를 따로 적어줘. 기대 결과와 허용 범위가 아직 승인되지 않았다면 임의로 정하지 말고 사용자에게 확인해 줘.

```markdown
# 이번 작업 안내: <작업명>

이번에는 **<맡길 일: 구현 / 조사 / 검증>**을 부탁할게.
전체 진행과 마지막 확인은 내가 챙길 테니 아래 내용을 중심으로 처리해 줘.

## 1. 이번에 해결할 내용
- <어떤 문제를 해결하고, 어떤 결과가 나와야 하는지 적어줘>

## 2. 먼저 읽어볼 파일
- `<확인할 파일 경로 1>`
- `<확인할 파일 경로 2>`
- <참고용 소스 프로젝트가 있으면 확인된 절대경로, 없으면 생략>

## 3. 수정해도 되는 범위와 꼭 지켜줄 약속
- **수정해도 되는 파일:** `<허용 파일·폴더 / 조사·검증이면 수정 없음>`
- **실행해도 되는 확인 명령:** `<명령과 실행 환경 / 없으면 실행 없음>`
- **꼭 지켜줘:**
  - 지정하지 않은 파일과 기존 사용자 변경은 건드리지 마. 조사·검증을 맡았다면 프로젝트 파일을 새로 만들거나 수정·삭제하지 마.
  - `src/test/**`의 테스트 파일은 생성·수정·삭제하거나 건너뛰도록 바꾸지 마. 테스트 준비나 스펙 변경이 필요하면 필요한 변경점만 알려줘.
  - 외부 소스 프로젝트, `data/`, `backup/`, 기존 `target/` 산출물은 직접 수정·삭제하지 마. 위에서 허용한 명령의 자동 산출물과 4절에 지정한 새 GUI 증거 파일만 예외야. 기존 증거를 덮어쓰거나 삭제하지 마.
  - 실행 중인 DB에 SQL 등으로 직접 쓰거나 스키마를 적용하지 마. 스키마 변경이 필요하면 수정 허용 범위에 적힌 정의 파일만 다뤄줘.
  - 화면에서 데이터를 등록·수정·삭제하는 것도 4절에 적힌 사용자 승인 테스트 환경과 데이터 범위에서만 해줘. 운영 데이터와 기존 사용자 데이터는 건드리지 말고, 범위나 정리 방법이 불명확하면 멈추고 물어봐 줘.
  - `README.md`와 `docs/ai/project/verification-log.md` 같은 검증 상태 문서는 내가 기록할 테니 수정하지 마.
  - API 키·토큰 같은 비밀값과 운영 데이터는 로그·스크린샷·보고에 노출하지 마. 커밋·푸시도 하지 말고 작업 상태 그대로 둬.
- **근거도 같이 알려줘:** 업무 규칙, 권한, 상태값, DB 컬럼 의미를 설명할 때는 근거 파일 경로와 줄 번호를 적어줘. 근거를 못 찾았으면 추측하지 말고 `미확인`이라고 남겨줘.
```

## 8. Orca 명령 (실측 확인된 것)

아래는 **총괄이 도구를 실행할 때만 보는 명령 참고**야. 작업 지시서나 사용자용 안내에 복사하지 마. 명령 이름과 도구가 요구하는 값은 실제 동작에 필요하니 바꾸지 말고, 사용자가 읽는 설명은 7장의 구어체 형식으로 써줘. `<...>` 부분은 실제 확인한 값으로 채워줘.

```powershell
# 1. 현재 상태와 열린 터미널을 확인해 줘
orca status --json
orca terminal list --json          # agentIdentity에서 Freebuff/OpenCode 터미널 핸들을 확인해 줘

# 2. Freebuff에 새 작업을 맡겨줘. --keep-open은 쓰지 마(5장)
# 7장의 구어체 지시서를 파일로 전달해 줘. --spec-file 사용은 확인됐어
orca orchestration worker-start --agent freebuff --worktree current --spec-file "<구어체 지시서 파일 경로>" --json

# 3. 필요할 때만 OpenCode2(Sol)에 맡겨줘. KR bridge를 먼저 확인해 줘(3장)
# 같은 작업 묶음으로 관리하려면 --run에 받은 값을 넣어줘(2026-11-18 확인)
orca orchestration worker-start --agent opencode2 --worktree current --run <runId> --spec-file "<구어체 지시서 파일 경로>" --json

# 4. 이미 열린 OpenCode2 등에 보낼 때는 --worktree, --model을 함께 쓰지 마
# 실행 중인 Freebuff나 사용자가 대화 중인 터미널에는 보내지 마(4.2절)
orca orchestration worker-start --terminal <term_handle> --spec "<작업 지시>" --json

# 5. 작업을 시작한 뒤 차례를 마치고 기다려줘
# Orca가 결과를 알리면서 알려주는 check 명령만 실행해 줘
orca orchestration check --run <runId> --terminal <총괄 terminal handle>

# 6. 진행 상황이 필요할 때 한 번만 확인해 줘. 반복 조회하지 마
orca orchestration worker-read --dispatch <dispatchId> --source auto

# 7. 다음 지시도 구어체로 써줘. 닫힌 작업은 새로 열리고 이전 대화 기억이 없어
# 실행 중인 Freebuff에는 보내지 마(4.2절)
orca orchestration send --to dispatch:<dispatchId> --subject "<제목>" --body "<구어체 지시>" --json

# 8. 맡긴 작업들의 상태를 확인해 줘
orca orchestration worker-list --run <runId> --json
```

- **기다리려고 `check --wait`를 쓰거나 `check`를 반복 실행하지 마.** 직접 조회하면 결과 알림을 먼저 가져가서 Orca가 총괄을 깨울 신호가 사라질 수 있어(`orca skills get orchestration` 기준). 원 기록의 대기 방식은 쓰지 마.
- `--agent opencode`(OpenCode 1)는 Orca에서 비활성 상태야(`agent_unconfigured`).
- `worker-start`가 실패하면 그대로 재시도하지 말고 실패 단계(`failedStage`)를 확인해 줘. 복구 안내는 `orca skills get orchestration --reference references/recovery-and-cleanup.md`로 확인할 수 있어.
- Orca 데스크톱 화면 없이 CLI만으로 제어할 수 있어. 자세한 사용법은 `orca skills get orchestration --full`, 자동 종료 동작은 5장을 확인해 줘.
