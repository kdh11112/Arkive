# 공통 검증 절차

> 이식 구분: 복붙 가능. 방법은 그대로 복사하고, 기대값만 대상 프로젝트의 정책·계약에서 가져온다.

이 문서는 검증을 계획하고 증거를 남기는 공통 방법을 정의한다. 대상 기능, 업무 기대값, 권한, 데이터, 환경, 보존 기간과 운영 기준은 Arkive 프로젝트 지식 및 담당자 확인으로 정한다. 자동화 도구가 설정되어 있지 않으면 수동 절차를 자동화가 있는 것처럼 보고하지 않는다.

## 검증 계획

1. 변경 목적과 관련 Acceptance Criteria를 확인한다.
2. 변경 전 기준(Baseline), 관련 사용처, 영향을 받는 계층과 데이터 범위를 확인한다.
3. 위험과 영향에 맞게 검증할 화면, API, DB, 로그, 기존 기능을 고른다.
4. 테스트 환경과 테스트 데이터가 안전한지 확인한다.
5. 기대 결과, 실제 결과, 판정과 증거 위치를 연결해 기록한다.

Acceptance Criteria나 기대 결과가 정해지지 않은 경우 임의의 결과를 만들지 않는다. 담당자 확인이 필요하다는 점을 남기고, 확인 가능한 독립 작업은 계속 진행한다.

## Verifier

- 검증 방법은 공통 표준을 따르되, 정답의 기준은 프로젝트의 업무 정책, API 계약, DB 정의, Acceptance Criteria 또는 승인된 변경 명세에서 가져온다.
- 자동 비교기를 추가할 경우 입력과 기대 결과의 출처, 비교 범위, 허용 오차, 실패 시 동작을 명시한다.
- 단순히 요청이 성공하거나 화면이 렌더링된 사실만으로 업무 결과가 맞다고 판단하지 않는다. 상태·권한·데이터 정합성 등 해당 조건을 확인한다.
- 통과, 실패, N/A, 미수행을 구분하고 검증 근거를 남긴다. 자세한 항목은 [test-standard.md](test-standard.md)와 [evidence-report-template.md](evidence-report-template.md)를 따른다.

## Guard

- Guard는 위험한 변경을 사전에 검토·차단하는 절차 또는 실제 자동화 검사다. 검사 도구가 존재하는지 확인하고, 수동 체크를 자동 Guard라고 표현하지 않는다.
- 공통으로 보안, 데이터 손실, API/스키마 호환성, 변경 범위 및 비밀정보 노출을 검토한다.
- 프로젝트별 차단 조건(예: 특정 환경의 DDL 금지, 승인 대상, 허용 경로, 민감 데이터 제한)은 담당자가 확인한 규칙으로만 등록한다.
- Guard 실패 시 원인과 영향 범위를 남기고, 우회나 예외 처리는 근거와 승인 주체가 확인된 경우에만 기록한다.

## Baseline과 Snapshot

- Baseline은 결과 비교 기준이다. 코드 변경은 가능하면 변경 전 Commit SHA, SVN Revision 등 버전 식별자를 기록하고, 런타임 비교는 환경·설정·데이터 조건도 함께 기록한다.
- Snapshot은 변경 전 상태를 보존하는 자료(화면, 응답, 조회 결과, 설정 또는 데이터 백업 등)다. 비교 목적과 복구 필요성에 맞는 자료만 만든다.
- Baseline과 Snapshot의 대상, 생성 시각, 환경, 출처, 저장 위치 및 복원 절차를 기록한다.
- 개인정보, 인증 정보, 비밀값, 운영 데이터가 포함될 수 있는 자료는 최소화하고 마스킹한다. 보관 위치와 기간은 프로젝트의 보안·운영 기준을 따른다. 기준이 미확인이라면 임의 저장하지 말고 담당 확인을 받는다.
- Snapshot을 생성했다는 사실만으로 복구 가능하다고 보지 않는다. 필요한 변경은 별도로 복원 절차를 확인한다.

## Runtime 검증

- Runtime 검증은 소스 정적 검토를 넘어 변경 특성에 맞게 실행 결과를 확인하는 절차다. 모든 변경에 모든 계층을 강제하지 않는다.
- 해당하는 경우 화면/DOM, 브라우저 콘솔, 네트워크 요청, API 응답과 상태 코드, 서버 로그, DB 결과를 이어서 확인한다.
- 검증 대상 URL, 화면, API, DB 객체, 계정, 환경 및 기대 결과는 프로젝트별 문서와 승인된 테스트 조건에서 확인한다.
- 실행 전 대상 환경과 데이터의 안전성을 확인한다. 운영 장애 유발, 무단 데이터 수정, 실제 외부 발송 등 영향이 있는 검증은 통제된 환경과 승인된 절차 없이 수행하지 않는다.
- 실행 버전, 조건/명령, 결과, 오류 및 증거 위치를 기록한다. 환경을 재현할 수 없으면 그 제한과 미검증 범위를 기록한다.

## Health와 Canary

- Health는 프로젝트별로 필요한 가용성·준비 상태 지표와 확인 경로를 정한다. Actuator 의존성이 있다는 사실만으로 엔드포인트 공개 여부나 Health 기준이 정해진 것으로 보지 않는다.
- Canary는 배포 구조가 점진 배포를 지원하는 프로젝트에서만 사용한다. 대상 비율/범위, 관찰 지표, 진행·중지 조건, 롤백 경로를 운영 담당자가 확인해 둔 경우에 수행한다.
- Canary 또는 Health 기준이 확인되지 않았으면 해당 항목을 적용하지 않거나 `미정`으로 남긴다. 성공 임계치나 배포 승인 기준을 추측하지 않는다.
