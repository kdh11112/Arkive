# 공통 SQL 및 데이터베이스 표준

> 이식 구분: 복붙 가능. 타 프로젝트에 그대로 복사해서 사용한다. DB 제품별 문법만 대상에 맞춘다.

대상 DB, 버전, 데이터 접근 도구 및 환경은 프로젝트 문서와 설정에서 확인한다. 아래 원칙은 DB별 문법이나 프로젝트별 마이그레이션 방식을 대신하지 않는다.

## SQL 작성

- 운영 SQL은 필요한 컬럼을 명시하고, JOIN 조건과 집계 단위를 분명히 작성한다.
- 운영 코드의 `SELECT *`는 지양한다. 개발 중 임시 조회나 데이터 확인 목적의 SQL까지 일률적으로 금지하지는 않는다.
- 사용자 입력은 데이터 접근 도구가 제공하는 안전한 파라미터 바인딩을 사용한다. SQL 문자열을 직접 조합해야 하는 동적 식별자는 허용 목록으로 제한한다.
- UPDATE와 DELETE는 식별 가능한 WHERE 조건을 둔다. 조건 변경 시 대상 범위와 예상 건수를 확인한다.
- 특별한 사유 없이 전체 행을 대상으로 하는 UPDATE/DELETE를 작성하지 않는다. 대량 변경은 대상 건수, 조건, 실행 환경, 트랜잭션, 백업 또는 복구 방법을 확인한다.
- 중요한 데이터 변경은 실행 후 영향 행 수와 결과 데이터를 확인한다. 예상 건수와 실제 영향 건수가 다르면 추가 변경을 진행하기 전에 원인을 확인한다.
- 가능한 경우 PK, Unique Key 또는 업무상 유일 식별자를 조건에 사용하고, 복합 조건은 각 조건의 의미를 확인한다.
- 암시적 JOIN보다 ANSI JOIN을 사용한다. JOIN 조건 누락으로 불필요한 Cartesian Product가 생기지 않는지 확인한다.
- NULL, 빈 문자열, 기본값의 의미는 현재 DB 및 업무 규칙을 확인한다.
- `IS NULL`과 `= ''`은 같은 조건으로 취급하지 않는다. Oracle은 빈 문자열을 NULL로 처리하는 등 DB별 차이가 있으므로 대상 DB와 저장 데이터 규칙을 확인한다.
- 대량 조회에는 사용 목적에 맞는 페이징·건수 제한을 고려한다. 기존 프로젝트의 페이징 방식을 확인하고 임의로 바꾸지 않는다. 단순 조회에 페이징을 무조건 적용하지 않는다.
- 페이지 간 중복이나 누락을 피할 수 있도록 페이징 결과의 정렬 기준을 확인하고, 가능하면 유일성을 보장하는 보조 정렬 키를 둔다.
- 1:N JOIN을 포함한 COUNT/SUM 등은 중복으로 집계 결과가 부풀려지지 않는지 확인한다.
- 대량 데이터, LIKE 및 광범위 검색, WHERE 절 함수, 서브쿼리, GROUP BY/ORDER BY, 복합 JOIN, 페이징 없는 대량 조회 및 대량 변경은 성능과 인덱스 영향을 확인한다. 필요한 경우 실행계획을 확인한다.

## MyBatis 사용 시

- 사용자 입력값은 `#{}` 바인딩을 우선 사용한다.
- `${}`는 컬럼명, 정렬 기준 등 SQL 식별자를 동적으로 구성해야 하는 경우에 한해 사용하고, 허용 목록으로 값을 제한한다. 바인딩으로 대체할 수 있는 값에는 `${}`를 사용하지 않는다.

## 페이징과 DB별 문법

페이징 및 SQL 문법은 프로젝트에서 확인한 DB 제품과 버전에 맞춘다. 아래는 가능한 방식의 예이며 프로젝트의 기존 방식을 우선한다.

| DB | 페이징/문법 예 |
| --- | --- |
| Oracle | `ROW_NUMBER()`, 지원 버전의 `OFFSET / FETCH`, `ROWNUM`, `SYSDATE`, `TO_CHAR()`, `TO_DATE()` |
| PostgreSQL | `LIMIT`, `OFFSET`, `nextval(...)` |
| MySQL / MariaDB | `LIMIT`, `CONCAT()` |

예약어와 충돌하는 객체명은 프로젝트의 기존 방식과 해당 DB 규칙을 따른다. 여러 DB를 지원하면 DB 특화 문법을 최소화하거나, 프로젝트에 이미 정해진 DB별 분기 방식을 유지한다.

## 데이터 변경 및 스키마

- DB 변경 전 대상 환경, 영향 기능, 데이터 보존 여부, 트랜잭션 및 복구/롤백 방법을 확인한다. 운영 데이터를 임의로 변경하지 않는다.
- 대량 데이터 변경은 실행 전후 건수와 조건을 확인하고, 복구가 필요한 경우 백업 또는 검증된 복구 방법을 준비한다. 트랜잭션 사용 가능 여부와 범위를 대상 환경 및 변경 규모에 맞게 확인한다.
- DDL의 트랜잭션 및 자동 커밋 동작은 DB와 실행 도구에 따라 다를 수 있으므로, 트랜잭션만으로 롤백 가능하다고 가정하지 않는다.
- 스키마 변경은 테이블, 컬럼, 자료형, PK/FK, Unique 제약조건, 인덱스, 시퀀스, 트리거 등 관련 객체와 DDL/초기화 스크립트, Mapper, 기존 데이터 및 배포 순서를 함께 검토한다.
- 마이그레이션이 필요한 변경은 가능한 경우 변경 SQL, 사전 조건, 사후 확인 및 복구 절차를 함께 기록한다.
- SQL 문법과 페이징, 문자열 연산, 식별자 생성 동작은 대상 DB에서 확인한다. 한 DB에서 동작한다는 이유만으로 다른 환경과의 호환성을 가정하지 않는다.
- 변경 기록에는 가능한 경우 대상 객체, 변경 이유, 적용 SQL, 영향 기능, 사후 확인 결과 및 롤백/복구 방법을 남긴다. 공통 적용 절차는 [migration-standard.md](migration-standard.md), Arkive의 확인된 마이그레이션 현황은 [migration.md](../project/migration.md)를 참고한다.
