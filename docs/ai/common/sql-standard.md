# 공통 SQL 및 데이터베이스 표준

> 이식 구분: 가이드형. 파일째 복사하되, 적용할 때는 대상 DB·프로젝트 값으로 판단하고, 읽었다는 이유만으로 끝냈다고 보지 않는다.

대상 DB, 버전, 데이터 접근 도구 및 환경은 프로젝트 문서와 설정에서 확인한다. 아래 원칙은 DB별 문법이나 프로젝트별 마이그레이션 방식을 대신하지 않는다.

## SQL 작성

- 운영 SQL은 필요한 컬럼, JOIN 조건과 집계 단위를 명시한다. `SELECT *`는 지양하되 개발 중 임시 조회·데이터 확인까지 일률적으로 금지하지 않는다.
- 사용자 입력은 데이터 접근 도구가 제공하는 안전한 파라미터 바인딩을 사용한다. SQL 문자열을 직접 조합해야 하는 동적 식별자는 허용 목록으로 제한한다.
- UPDATE/DELETE는 식별 가능한 WHERE 조건을 두고 가능하면 PK·Unique Key·업무상 유일 식별자를 쓴다. 복합 조건의 의미, 대상 범위와 예상 건수를 확인한다.
- 특별한 사유 없이 전체 행을 대상으로 하는 UPDATE/DELETE를 작성하지 않는다. 대량 변경은 대상 건수, 조건, 실행 환경, 트랜잭션, 백업 또는 복구 방법을 확인한다.
- 중요한 데이터 변경은 실행 후 영향 행 수와 결과 데이터를 확인한다. 예상 건수와 실제 영향 건수가 다르면 추가 변경을 진행하기 전에 원인을 확인한다.
- 암시적 JOIN보다 ANSI JOIN을 사용한다. JOIN 조건 누락으로 불필요한 Cartesian Product가 생기지 않는지 확인한다.
- NULL·빈 문자열·기본값의 의미는 DB와 업무 규칙으로 확인한다. `IS NULL`과 `= ''`을 같은 조건으로 보지 않는다(Oracle은 빈 문자열을 NULL로 처리).
- 대량 조회에는 사용 목적에 맞는 페이징·건수 제한을 고려한다. 기존 프로젝트의 페이징 방식을 확인하고 임의로 바꾸지 않는다. 단순 조회에 페이징을 무조건 적용하지 않는다.
- 페이지 간 중복이나 누락을 피할 수 있도록 페이징 결과의 정렬 기준을 확인하고, 가능하면 유일성을 보장하는 보조 정렬 키를 둔다.
- 1:N JOIN을 포함한 COUNT/SUM 등은 중복으로 집계 결과가 부풀려지지 않는지 확인한다.
- 대량 데이터, LIKE 및 광범위 검색, WHERE 절 함수, 서브쿼리, GROUP BY/ORDER BY, 복합 JOIN, 페이징 없는 대량 조회 및 대량 변경은 성능과 인덱스 영향을 확인한다. 필요한 경우 실행계획을 확인한다.

## MyBatis 사용 시

- 사용자 입력값은 `#{}` 바인딩을 우선 사용한다.
- `${}`는 컬럼명, 정렬 기준 등 SQL 식별자를 동적으로 구성해야 하는 경우에 한해 사용하고, 허용 목록으로 값을 제한한다. 바인딩으로 대체할 수 있는 값에는 `${}`를 사용하지 않는다.

## 페이징과 DB별 문법

페이징 및 SQL 문법은 프로젝트에서 확인한 DB 제품과 버전에 맞춘다. 아래는 가능한 방식의 예이며 프로젝트의 기존 방식을 우선한다.

| DB | 페이징/문법 예 |
| --- | --- |
| Oracle | `ROW_NUMBER()`, 지원 버전의 `OFFSET / FETCH`, `ROWNUM`, `SYSDATE`, `TO_CHAR()`, `TO_DATE()` |
| PostgreSQL | `LIMIT`, `OFFSET`, `nextval(...)` |
| MySQL / MariaDB | `LIMIT`, `CONCAT()` |

예약어와 충돌하는 객체명은 프로젝트의 기존 방식과 해당 DB 규칙을 따른다. 여러 DB를 지원하면 DB 특화 문법을 최소화하거나, 프로젝트에 이미 정해진 DB별 분기 방식을 유지한다.

## 데이터 변경 및 스키마

- DB 변경 전 대상 환경, 영향 기능, 데이터 보존 여부, 트랜잭션 및 복구/롤백 방법을 확인한다. 운영 데이터를 임의로 변경하지 않는다.
- 대량 변경의 건수·조건·결과 확인은 위 SQL 작성 기준을 따르고, 백업 또는 검증된 복구 방법과 트랜잭션 범위를 준비한다.
- DDL의 트랜잭션 및 자동 커밋 동작은 DB와 실행 도구에 따라 다를 수 있으므로, 트랜잭션만으로 롤백 가능하다고 가정하지 않는다.
- 스키마 변경은 테이블, 컬럼, 자료형, PK/FK, Unique 제약조건, 인덱스, 시퀀스, 트리거 등 관련 객체와 DDL/초기화 스크립트, Mapper, 기존 데이터 및 배포 순서를 함께 검토한다.
- SQL 문법과 페이징, 문자열 연산, 식별자 생성 동작은 대상 DB에서 확인한다. 한 DB에서 동작한다는 이유만으로 다른 환경과의 호환성을 가정하지 않는다.
- 변경 기록에는 객체·이유·SQL·영향 기능·사전 조건·사후 확인·복구 절차를 남긴다. 계획·적용 순서는 [migration-standard.md](migration-standard.md), 실제 현황은 대상의 프로젝트 지식에서 확인한다.

## DB 변경을 어느 파일에 넣을지

먼저 **객체 정의인지, 최초 실행에 필요한 값인지, 실행 중 생기는 업무 데이터인지**를 구분한다. 파일 이름만 보고 모든 INSERT를 시드로 넣지 않는다.

| 변경 내용 | 위치 | 예 / 주의 |
| --- | --- | --- |
| 테이블·컬럼·자료형·기본값·PK/FK·Unique/Check·인덱스·시퀀스 등 최종 구조 | `schema.sql` 또는 대상의 스키마 정의 | 새 기능 테이블, 컬럼 길이 확장, 검색 인덱스. 최신 스키마 방식이면 변경 결과를 최종 CREATE 정의에 반영한다 |
| 빈 DB에서 기능을 시작하는 데 필수인 초기값 | `seed.sql` 또는 대상의 초기값 스크립트 | 메뉴·필수 시스템 코드·역할·사용자-역할·메뉴 권한·ID 생성기 시작값. 선행 객체와 참조 관계를 함께 준비한다 |
| 사용자가 등록하거나 업무 처리로 생성·수정·삭제하는 값 | 기존 Mapper/XML·Service 등 정상 업무 경로 | 게시물·신청·예약·회의실·연차 부여·파일 메타데이터·로그·토큰·사용자 동의 이력. 테스트 fixture와 백업 덤프도 필수 시드가 아니다 |
| 이미 사용 중인 DB의 구조 변경·백필·초기값 갱신 | 대상의 승인된 마이그레이션/배포 절차 | `schema.sql`을 고쳤다고 기존 DB가 갱신되는 것은 아니다. 보존·권한·중복·복구를 검토한 별도 변경 SQL을 준비한다 |

- 새 기능은 `schema`의 객체와 `seed`의 메뉴·역할 의존성, Mapper/XML·Service·설정을 함께 확인한다. 메뉴만 만들고 접근 권한을 빠뜨리거나 새 메뉴에 일반 사용자 권한을 일괄 부여하지 않는다.
- 시드는 **필요한 최소값**만 둔다. 개발용 계정·약관 자리표시자는 데모용임을 표시하고, 실제 비밀번호·토큰·개인정보·운영 값은 넣지 않는다. 법무·업무·권한 정책을 시드로 추정하지 않는다.
- 최신 `schema.sql` + 필수 `seed.sql`은 빈 DB 초기화용이다. 최초 한 번 `schema` → `seed`로 실행하고, 일반 코드 수정·서버 재시작 때 기존 DB를 다시 CREATE하거나 시드를 덮어쓰지 않는다.
- 초기화 실패 DB를 빈 DB로 오인하지 않게 완료 상태를 구분한다. DDL 부분 생성이나 시드 실패를 자동 삭제·무조건 재실행으로 숨기지 않는다.
- 최신 정의를 관리하는 프로젝트와 버전 마이그레이션을 누적하는 프로젝트를 구분한다. 대상이 Flyway/Liquibase 등 기존 절차를 쓰면 그 절차를 유지하고 데모 초기화기를 복사하지 않는다.

실제 경로·초기화 조건·기존 DB 처리 방법은 프로젝트의 DB 기록에 남긴다. 운영·보존 DB의 변경은 [migration-standard.md](migration-standard.md)를 따른다.
