# 공통 코딩 표준

> 공통 방법(복사 가능). 실제 구조·설정·정책은 대상의 프로젝트 지식과 코드에서 확인한다. 이 문서만으로 구현·검증 완료를 판단하지 않는다.

Java 웹 프로젝트에 적용한다. 트랙별 보충은 [이식 가이드](../../../PORTING.md)에서 선택하며 반대 트랙은 읽지 않는다. 일반 원칙으로 업무 정책이나 계약을 추정하지 않는다.

## 기존 구조 우선

- 변경 전 관련 구현과 호출 흐름을 확인하고 기존 구조, 명명, 예외 처리, 로깅, 데이터 접근, 트랜잭션 및 빌드 방식을 따른다.
- 계층과 책임은 프로젝트 구조에 맞춘다. 특정 프레임워크나 계층 구성을 모든 프로젝트에 강요하지 않는다.
- 기존 공통 기능과 의존성을 먼저 찾고, 근거 없이 중복 유틸리티나 새 라이브러리를 추가하지 않는다.

## 계층별 책임

- Controller는 HTTP 요청 수신, 파라미터 바인딩, 기본 입력 검증, 인증·인가 연계, Service 호출 및 화면/API 응답 반환을 담당한다. 복잡한 업무 규칙과 SQL/DB 처리를 두지 않는다.
- Service/ServiceImpl은 비즈니스 로직과 업무 정책, 여러 DAO/Mapper 호출의 조합 및 필요한 트랜잭션 처리를 담당한다. 트랜잭션 방식은 기존 구현과 프로젝트 설정을 따른다.
- DAO/Mapper는 데이터 조회·등록·수정·삭제를 담당한다. SQL은 프로젝트의 Mapper/XML 또는 기존 데이터 접근 방식을 우선하고, 큰 SQL 문자열을 업무 코드에 직접 작성하지 않는다.
- JSP, Thymeleaf 등 화면 계층은 표시, 사용자 입력 및 인터랙션을 담당한다. 업무 규칙의 최종 검증을 화면에만 맡기지 않는다.

## 명명

프로젝트별 명명 규칙을 우선한다. 별도 규칙이 없을 때 Java 코드에는 일반적인 관례를 적용한다.

- 클래스와 인터페이스: `PascalCase` (예: `EvaluationService`)
- 메서드와 변수: `camelCase` (예: `selectEvaluationList`, `userId`)
- 상수: `UPPER_SNAKE_CASE` (예: `MAX_PAGE_SIZE`)
- Mapper 메서드와 SQL ID는 서로 대응되게 관리한다.

## 예외 및 로깅

- 예외를 빈 `catch` 블록으로 숨기거나 무시하지 않는다. 처리할 때는 필요한 로그, 적절한 예외 변환, 트랜잭션 결과와 사용자 응답을 프로젝트의 예외 처리 방식에 맞춘다.
- `printStackTrace()`나 표준 출력으로 운영 오류를 기록하지 않는다.
- 장애를 추적할 수 있도록 필요한 범위에서 기능/작업 구분, 안전한 업무 식별자, 처리 단계, 오류 코드 및 예외 원인을 기록한다.
- 로그·문서에 비밀번호, 인증 토큰, 세션 정보, 비밀값, 전체 요청 본문 또는 불필요한 개인정보를 포함하지 않는다. 필요한 업무 로그도 프로젝트의 개인정보 규칙을 따른다.
- 기존 로거와 로깅 체계를 재사용한다.

## 화면 및 JavaScript

- 화면은 기존 템플릿 엔진·레이아웃·요청/오류 표시 방식을 따른다. 업무 로직이나 서버 검증을 대신하는 규칙을 두지 않는다.
- JSP 화면에서는 Scriptlet 사용을 지양하고, 기존 프로젝트가 사용하는 JSTL/EL 등 표현 방식을 우선한다.
- Thymeleaf는 `th:*`와 기존 layout·fragment를 사용하고 HTML 구조와 표현식을 분리한다.
- JavaScript는 기존 라이브러리와 작성 방식에 맞춘다. 가능한 경우 전역 변수와 중복 코드를 줄이고 함수의 책임과 변수명을 명확히 한다.
- 비동기 요청에는 성공뿐 아니라 서버 오류와 통신 실패도 처리하고, 사용자에게 적절한 결과를 표시한다. 공통 JavaScript를 변경하면 사용하는 화면의 영향 범위를 확인한다.

### CSS·반응형 화면

- **13.3인치 노트북은 필수 확인 대상이다.** 해당 노트북의 실제 해상도·OS 표시 배율·브라우저 확대율·콘텐츠 viewport를 기록하고, 주요 화면의 목록·입력·상세·메뉴·모달을 ego-browser로 확인한다.
- 인치만으로 CSS 해상도를 결정하지 않는다. 13.3인치를 임의의 고정 픽셀 크기로 간주하거나, 큰 모니터에서 창만 줄인 검사를 실제 13.3인치 기기 검증으로 표시하지 않는다. 기기를 사용할 수 없으면 대체 viewport 확인과 실제 기기 `미수행`을 구분한다.
- 나머지 화면은 특정 인치에 고정하지 않는다. 24·30인치 등 큰 화면에서도 해상도·배율·창 크기에 따라 자연스럽게 늘고 줄어야 한다. 큰 창뿐 아니라 중간 폭과 창을 줄인 상태도 확인한다.
- 기존 레이아웃을 우선하고, `%`·flex/grid·`minmax()`·`min-width: 0`·`max-width`·`clamp()` 등 콘텐츠에 맞는 유동 폭을 사용한다. breakpoint는 화면이 깨지는 폭을 근거로 정하며 인치별 CSS나 데스크톱 고정 폭을 추가하지 않는다.
- 페이지 전체의 불필요한 가로 넘침, 잘리는 버튼·입력·메뉴, 겹치는 텍스트·차트, 화면 밖으로 나가는 모달을 막는다. 표·에디터·차트가 넓으면 내용 특성에 맞춰 줄바꿈·재배치·전용 스크롤 영역을 제공하고, `overflow: hidden`으로 필수 정보를 숨겨 해결하지 않는다.
- 공통 CSS 변경은 이를 쓰는 대표 화면에 회귀 확인을 한다. 확인 범위·도구·판정은 [test-standard.md](test-standard.md#화면-크기-확인)를 따른다.

## 입력값 검증

- 사용자 입력과 외부 데이터를 신뢰하지 않으며 기존 검증·오류 처리 방식을 재사용한다.
- 클라이언트 검증은 사용성을 돕고 서버 검증은 보안 및 데이터 무결성을 보장하도록 역할을 나눈다. 클라이언트 검증만으로 서버 검증을 대체하지 않는다.
- 업무와 관련된 경우 서버에서 권한, 필수값, 상태, 허용 범위, 사용자 소유권 및 중복 요청을 확인한다.

## 보안 및 변경 범위

- SQL Injection, XSS, CSRF, 인증·권한 우회, 민감정보 노출, 파일 업로드 취약점, 경로 조작과 안전하지 않은 입력 처리를 점검한다. 기존 보안 프레임워크·공통 모듈을 우선한다.
- 출력 인코딩과 파일 처리는 기존 보안 체계에 맞춘다. 서버 검증은 위 입력값 검증 기준을 따른다.
- API 계약, 데이터 스키마, 공통 컴포넌트 및 환경 설정을 변경하기 전에 사용처와 영향 범위를 찾는다.
- 다른 프로젝트의 기능을 가져올 때 코드를 그대로 복사하지 말고 업무 규칙, 권한, 데이터 구조, 외부 연계, 의존성 및 설정을 대상 프로젝트에 맞춘다.

## 중복 코드 및 리팩터링

- 중복 발견만으로 대규모 리팩터링을 하지 않는다. 목적·영향 범위를 확인하고 기존 기능의 안전한 유지를 우선한다.
- 요청과 무관한 구조 개선·기술 도입·파일 이동·이름 변경은 별도 작업으로 분리한다.
