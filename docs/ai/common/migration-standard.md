# 공통 DB 마이그레이션 절차

> 이식 구분: 복붙 가능. 타 프로젝트에 그대로 복사해서 사용한다. 실제 도구·승인·백업은 대상 프로젝트에서 채운다.

이 문서는 DB 구조·데이터 변경을 계획하고 검증하는 공통 방법을 정의한다. 실제 도구, 환경, 승인자, 실행 순서와 백업 정책은 각 프로젝트의 [migration.md](../project/migration.md) 및 운영 기준에서 확인한다.

## 계획과 사전 확인

1. DB 제품·버전, 대상 환경, 적용 권한 및 데이터 소유자를 확인한다.
2. 변경 전 스키마·데이터 Baseline, 영향 기능, Mapper/SQL, 배치 및 외부 소비자를 확인한다.
3. 변경 스크립트, 선행 조건, 적용 순서, 예상 건수/잠금/중단 영향과 민감 데이터 영향을 검토한다.
4. 백업 또는 대상 환경에서 검증된 복구 방법을 마련한다. DDL이 트랜잭션으로 롤백된다고 가정하지 않는다.
5. 개발/검증 환경에서 적용과 사후 검증을 수행하고, 운영 적용이 필요한 경우 프로젝트 승인 절차를 따른다.

## 적용 및 사후 검증

- 계획된 버전과 대상이 일치하는지 확인한 뒤 승인된 절차로 적용한다.
- 스키마 정의, 제약조건, 영향 행 수, 데이터 정합성, 주요 SQL과 관련 기능을 확인한다.
- 실패 시 추가 변경을 멈추고, 원인·영향·복구 판단을 기록한다.
- 스크립트 버전, 대상 환경, 실행 시각, 결과, 실행자/승인자, 검증 근거와 남은 위험을 기록한다.
- 복구 방법을 실제로 검증하지 않았다면 검증된 복구라고 표현하지 않는다.

SQL 작성·대상 범위·DB별 문법은 [sql-standard.md](sql-standard.md)를 따른다.
